# CAT Operator Copilot

A **Smart Operator Assistant for CAT Machinery** — a tablet-first "operator companion"
built for the Caterpillar Digital Hackathon. One cohesive product, not a bundle of
pages, centred on three differentiators:

1. **Voice-assisted operator assistant** (multilingual, context-grounded)
2. **Shift logging / AI shift handover**
3. **Weather-aware task management** (optimizer + what-if simulator)

Supporting features: operator dashboard, task time estimation, safety insights,
anomaly detection, and lightweight training.

> ⚠️ All data is **synthetic** hackathon data. Values do **not** represent official
> Caterpillar operating thresholds, policies, or specifications.

---

## Stack

- **Python 3.9+ / FastAPI** backend (API + server-rendered UI)
- **Jinja2 templates + vanilla JS** frontend (no build step)
- **Deterministic synthetic dataset** generated by a seeded PRNG
- **Optional** Anthropic Claude for natural phrasing (falls back to a deterministic,
  data-grounded responder)
- **Optional** Google Cloud Speech-to-Text / Text-to-Speech behind a provider
  abstraction (falls back to the browser Web Speech API)

Everything runs with **zero external keys** — the demo is fully functional offline.

---

## 🛰️ Offline-first (the USP)

Construction sites often have **no connectivity**. CAT Operator Copilot is
**edge-first**: the entire operator brain runs **on the device**, so it keeps
working with the internet completely down.

| Capability | Offline? | How |
|-----------|:--------:|-----|
| Dashboard, tasks, shift, safety, training | ✅ | All data + logic are local Python |
| Task prediction, weather-aware optimizer, what-if | ✅ | Deterministic, on-device |
| Assistant **reasoning** (intent, context, answers, Hindi) | ✅ | On-device responder over local data — no LLM needed |
| Safety guardrail | ✅ | Local rule layer |
| Voice **input** (speech-to-text) | ✅ | **On-device Vosk** model (`/api/voice/transcribe`) — no cloud |
| Voice **output** (text-to-speech) | ✅ | Browser `speechSynthesis` (local voices) |
| Shift notes while offline | ✅ | Queued in the browser, auto-synced on reconnect |
| App shell loads with no network | ✅ | **PWA service worker** caches shell + last API data |
| Cloud LLM phrasing, Google STT/TTS | ☁️ optional | Enrichment only — skipped cleanly when offline |

**Voice engine priority** (`copilot/services/voice.py`): on-device Vosk →
Google Cloud (if creds) → browser Web Speech. When offline, the mic records
16 kHz WAV in the browser, POSTs it to the local server, and **Vosk transcribes
it on-device** — then the local assistant answers. The sidebar shows a live
**Online/Offline** badge and the active **voice mode**.

Enable on-device voice (downloads a ~40 MB model, one time):

```bash
bash scripts/get_models.sh      # or: python -m pip install vosk && download the model
```

Without the model, voice gracefully falls back to browser speech (online) or the
text box; every other offline capability still works. To force a mode:
`VOICE_PROVIDER=offline|google|browser`.

### Store-and-forward sync (edge → cloud)

Connectivity is treated as **intermittent, not a prerequisite**. Every
locally-generated change (shift notes, shift start/end) is written as an
**append-only event with a UUID** into a durable **SQLite outbox on the edge
device**. A background worker pushes un-synced events to the **central cloud
(PostgreSQL)** whenever it's reachable; ingest is **idempotent** (dedupe by
`event_id`), so retries never duplicate and the design is conflict-free.

```
[ Operator UI ] ─▶ [ Edge app + SQLite outbox ] ─(store-and-forward)─▶ [ Cloud + PostgreSQL ]
   PWA, on-device      always local, works offline     syncs when online     fleet event store
```

- **Edge app** (`app.py`, `:8000`) — the copilot; writes events to `data/edge.db`.
- **Cloud service** (`cloud_app.py`, `:9000`) — PostgreSQL-backed; `/cloud/ingest`
  (idempotent), `/cloud/events`, and a **live fleet dashboard** at `/`.
- **Sync** (`copilot/services/sync.py`) — auto-flush every 10 s when the cloud is
  reachable, plus a manual **"Sync now"** button on the Shift page which shows
  `N pending · last synced HH:MM · cloud reachable · device ID`.

**Run the full stack** (starts Postgres + cloud + edge):

```bash
bash scripts/run_all.sh
# Operator Copilot: http://localhost:8000   Cloud dashboard: http://localhost:9000
```

**Demo the resilience:** open the cloud dashboard; add a shift note (it appears
locally instantly); `pkill -f "uvicorn cloud_app"` to simulate the cloud going
away; add more notes → they queue on the edge ("N pending"); restart the cloud →
within 10 s the events flow into PostgreSQL and appear on the dashboard.

## Quick start

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python scripts/generate_data.py       # regenerate the synthetic dataset (deterministic)
uvicorn app:app --reload --port 8000  # run the app
```

Open http://localhost:8000

### Operator login

The app is gated by **operator authentication**. On first load you're sent to
`/login` — a tablet-style **PIN pad**. Pick an operator and enter their 4-digit PIN;
identity (operator + assigned machine) is then carried in a **signed, HTTP-only
session cookie**, and every API resolves who you are from that cookie server-side.

Sign out from the sidebar. The default demo operator (**Arjun**) has a live
in-progress shift ("now" = 11:05).

**Security notes:** PINs are stored only as salted PBKDF2-SHA256 hashes
(`data/credentials.json`); the cookie is HMAC-signed with `SESSION_SECRET` and
cannot be forged; identity is never taken from client query params once logged in.
Set a real `SESSION_SECRET` in production.

## Architecture

```
app.py                     FastAPI app: pages + JSON API
scripts/generate_data.py   Deterministic synthetic data generator (seeded)
data/*.json                Generated datasets
copilot/
  data.py                  Data access layer (loads JSON, time helpers)
  services/
    context.py             Resolves current operator/machine/task/shift/weather/safety
    weather.py             Forecast + synthetic weather->duration factor
    task_prediction.py     Transparent statistical duration predictor
    task_optimizer.py      Weather-aware reorder + What-If simulator
    shift.py               Shift summary + AI-style handover generator
    safety.py              Safety status + rule-based anomaly insights
    assistant.py           Intent detection, safety layer, bilingual responder, LLM
    voice.py               VoiceService abstraction (Google Cloud | browser) + note extraction
    store.py               In-memory runtime store (notes, shift state)
templates/                 Jinja2 page shells
static/                    styles.css, app.js (renders every page from the API)
```

**AI flow (grounded, no hallucinated data):**
`question → intent detection → build_context() (real data) → deterministic grounded
answer → optional LLM rephrasing (never contradicts the numbers) → safety validation`.
Safety-critical questions (leaks, fire, repairs…) bypass the LLM and return
conservative "stop and follow the manual / call a supervisor" guidance.

**Voice flow:**
`mic → backend /api/voice/transcribe → Google STT (if configured) or browser Web
Speech API → assistant → response → /api/voice/synthesize → Google TTS or browser
speechSynthesis`. Text input is always available as a fallback.

## API endpoints

| Method | Path | Purpose |
|-------|------|---------|
| GET | `/api/context` | Current operator/machine/task/shift/weather/safety |
| POST | `/api/assistant` | Ask the assistant (`text`, `language`, `operatorId`, `machineId`) |
| GET | `/api/tasks` | Today's tasks with duration predictions |
| GET | `/api/optimize` | Weather-aware reorder (add `rainHour` for What-If) |
| GET | `/api/safety` | Safety status + anomaly insights + incidents |
| GET/POST | `/api/shift` | Shift summary + handover; POST `note` / `start` / `end` |
| GET | `/api/operators` | Valid operator/machine pairings for the switcher |
| POST | `/api/voice/transcribe` | STT (Google or browser-fallback signal) |
| POST | `/api/voice/synthesize` | TTS (Google or browser-fallback signal) |

## Environment variables

Copy `.env.example` to `.env`. All are optional.

| Var | Effect |
|-----|--------|
| `ANTHROPIC_API_KEY` | Enables Claude for natural phrasing (else deterministic responder) |
| `ANTHROPIC_MODEL` | Model id (default `claude-opus-4-8`) |
| `GOOGLE_CLOUD_PROJECT_ID` / `GOOGLE_APPLICATION_CREDENTIALS` | Enable real Google Cloud voice |
| `VOICE_PROVIDER` | `auto` \| `google` \| `browser` |

Credentials stay on the backend only and are never sent to the frontend.
Install `google-cloud-speech` / `google-cloud-texttospeech` (see `requirements.txt`)
only if you enable real cloud voice.

## Demo script (≈3 min)

1. **Home** — "Good morning, Arjun." Current task (Trenching, in progress), next task,
   weather with a rain-at-14:00 warning, today's stats.
2. **Assistant** → "What do I have to do today?" — summarises the real shift.
3. **Assistant** → "Will the weather affect my work?" — reasons over synthetic weather + tasks.
4. **Assistant** → switch to **हिन्दी**, ask *"mera agla task kya hai"* — answers in Hindi.
5. **Tasks** → **Optimize My Day** — recommends resequencing weather-sensitive work
   before the rain, with explanations.
6. **Tasks** → **What-If** (rain at 13:00) — completion 14:28 → 14:40, optimized 14:09.
7. **Assistant** → *"There is a hydraulic leak"* — conservative safety guidance (no repair steps).
8. **Safety** — status, potential unusual patterns, incidents.
9. **My Shift** → add a voice/text note *"Trenching in Zone B was slower because of wet ground"*
   → **End Shift** → AI handover regenerates including the note.

## Known limitations / next steps

- Runtime notes & shift open/close are in-memory (reset on restart) — swap `store.py`
  for a real DB to persist.
- Task predictor is a transparent statistical baseline, not a trained ML model.
- Hindi is fully templated; Spanish/Tamil responses currently fall back to English
  text (TTS still speaks the selected voice). The architecture adds languages without
  touching core assistant logic.
- Google Cloud STT/TTS is wired but untested without credentials; browser fallback is
  the default.
- Next: persistence layer, richer per-language responses, trained duration model,
  multi-operator handover chaining, and offline PWA packaging for tablets.
